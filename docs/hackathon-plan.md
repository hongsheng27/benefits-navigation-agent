# Hackathon 計畫

2026 Taiwan Generative AI Application Hackathon **創意交流組**。

本文件記錄比賽的硬性條件、MVP 範圍決定、交付分工與風險備案。
產品定位見 [positioning.md](positioning.md),資料格式見 [data-model.md](data-model.md)。

|---|---|

| **決賽** | **8/1 – 8/2** |

決賽為**現場 30 小時開發**,含簡報與 Live Demo。賽前準備多少,現場就少做多少。

## 硬性條件

- **僅限使用 AWS 服務提供之基礎模型。** 需使用 AWS 雲服務或 AWS 生成式 AI 工具
  (含 Kiro IDE)。**Bedrock 是規則要求,不是技術選項。**
- 隊伍 2–5 人,全隊需出席決賽兩日才能取得完賽證明。
- 至少 2 名成員需完成全部 3 場生成式 AI 工作坊。

## 評分項目與對照

| 項目 | 我們的狀況 |
|---|---|
| 創意度 | 從人生事件切入、敢說「不符合」 |
| 技術可行性 | policy-governed 架構、ADR、可測試性 —— 強項 |
| 商業應用性 | 真實問題、明確使用者 |
| 主題切合度 | 對準**普惠 AI 獎** |
| **完成度** | **最大風險。評分寫的是「功能完整、體驗流暢」** |

**評分項目中沒有「AI 技術深度」。** 架構刻意限縮 LLM 的決策權不會扣分,
「技術可行性」反而獎勵它。但敘述上要說成「把 agent 用對地方」,
而不是「我們少用 AI」。

### 獎項

- 优选獎 1 隊(NT$40,000)
- **普惠 AI 獎 1 隊(NT$20,000)** —— 幫助剛喪偶的長輩與照顧者取得應有的福利,
  正對應這個獎項,簡報應明確往此靠攏

## MVP 範圍

情境維持**配偶死亡**。候選的「家人重病照護導航」牽涉醫療、長照、社福、身障四個
系統,前置認定各有流程,30 小時做不完,列為簡報中的未來方向。

### 一深三淺

不要四項福利都寫完整規則。

| | 做法 | 輸出 |
|---|---|---|
| **1 項做深** | 寫 `rules/`,完整資格判定 | 符合/不符合、差在哪一條、期限倒數 |
| **3 項做淺** | 只做福利卡與辦理順序 | 承辦機關、應備文件、順序;標示「未經資格判定」 |

Demo 只需要**一個**「不符合」的時刻。四項都寫規則會吃掉現場全部時間,
而評分看的是流程跑不跑得通,不是福利數量。

深度那一項建議選**有明確期限**的項目,因為「還剩 18 天」的效果最強,
而那是結構化條件才做得到的事。

### B 打底,A 加值

- **打底**:福利卡資料已足以支撐導航與說明,先讓完整流程跑起來
- **加值**:選定的 1–2 項寫成 `rules/`,提供可稽核的判定

畫面上必須明確區分哪些是**判定**、哪些是**參考資訊**。這是誠實,
也符合產品調性。

## Demo 必須看得見的四件事

風險不是做不出差異,是做出來了但看不見。

1. 系統**反問**一個通用模型不會主動問的必要條件
2. 出現 **`ineligible` 判定**,並指出差在哪一個條件
3. 判定旁的**官方依據連結**,含機關與日期
4. 帶**順序與期限**的辦理路徑

加分:現場打開結構化 log,展示 `tool_call_blocked` —— 模型試圖呼叫資格判定
工具而被狀態機擋下。這是可見的 agent 安全機制。

## 風險與備案

### 1. Bedrock 權限未經驗證

主辦回覆「應有」,但無具體清單。**必須自行驗證**,重點是實際呼叫一次
(`converse`),而非只確認模型列得出來 —— 列得出不代表帳號已獲授權。

若受限:調整模型優先序(`BEDROCK_MODEL_ID` 已是環境變數),或啟用 fallback。

### 2. 現場網路 / 服務失效

準備 `AgentRunner` 的 stub 實作,使用預錄的萃取結果。

因為資格判定在規則引擎、資料在本機 JSON,**沒有模型也能跑完整條流程**——
[positioning.md](positioning.md) 的「移除 LLM 系統仍可運作」正好就是 demo 保險。
真的用上時應誠實說明。

### 3. Strands 增加一層不確定性

[ADR-0004](decisions/0004-trial-strands-agent-runner.md) 已定退出條件。
**給 spike 一個截止日**;逾期未能穩定限制工具與產生結構化輸出,即改用
Bedrock API 直呼。現場才發現是最糟的情況。

### 4. 現場整合爆炸

進場前至少跑通一次「前端 → API → 狀態機 → 規則 → 前端」,內容是假的也可以。
第一次整合一定出問題,要讓它發生在賽前。

## 停止開發的時點

現場需提前 **4–6 小時**停止開發、轉入 demo 準備與彩排。
這個判斷由 Technical Lead 執行,而且一定會有人想再多加一個功能。
