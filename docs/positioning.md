# 產品定位:接住為什麼不是套皮 AI

這份文件回答一個會反覆出現的問題:**通用聊天模型已經能回答福利問題,這個專案的價值在哪?**

它不是對外文案,是團隊做取捨時的參照點。任何新功能、新技術選型或 demo 腳本,
都應該能對照這裡的判準說明它強化了哪一項差異;強化不了的,優先級應該往後排。

## 一句話

> 通用聊天模型回答「有哪些福利」。接住回答「你該做什麼」。

前者是知識問題,通用模型很強。後者是決策與流程問題,通用模型很弱。

## 誠實的起點

現在把「我先生過世了,我可以領什麼」貼進任何一個主流聊天模型,都會得到一份組織
良好、語氣得體、大致正確的清單。這是事實,團隊內部與對外說明都不應該假裝相反。

以下這幾點**不要拿來當差異點**,因為比不贏,而且會損害可信度:

- **同理心與語氣** — 通用模型的表達已經很好。
- **知識廣度** — 我們只覆蓋少數情境,對方覆蓋一切。
- **回答速度與流暢度** — 我們多了確定性檢查,只會更慢。

差異必須來自結構,不是來自話術。

## 四個真實差異

按重要性排序。愈前面的愈應該在 demo 中優先呈現。

### 1. 通用清單 vs 針對這個人的判定

聊天模型的回答長這樣:「**如果**你年滿一定年齡,**或**你扶養未成年子女,就可以請領……」

那個「如果」是關鍵。它把判斷責任交還給使用者,而使用者要的不是可能性清單,是
「**我**到底能不能領」。

要回答「我」,必須先確定一組條件:過世者的投保身分與年資、申請人年齡、是否扶養
未成年子女、申請人自身的工作與投保狀況等。這些條件的**組合**決定結果。

通用模型不會系統性地問完,因為它被訓練成一次給出完整回答。就算被要求發問,它也
不知道自己還缺哪些必要欄位。

接住的 `COLLECT_MISSING_FIELDS` 狀態由規則計算缺漏欄位,問到齊為止,而且知道還
缺什麼。**這是產品行為的差異,不是模型能力的差異** — 說明時不要暗示模型能力不足。

### 2. 平面清單 vs 有順序與期限的路徑

喪偶或家人重病之後,真正的困難不是「有哪些福利」,而是這些事情**彼此有依賴、而且
有時限**:某些登記有辦理期限、某份謄本要先取得才能辦後續申請、某些給付有請領時效、
身分未變更會持續產生費用。

> 具體的天數、時效與罰則以 `docs/official-sources.md` 收錄的官方文件為準。
> 本文件不列舉未查證的數字。

「先辦什麼、辦完才能辦什麼、哪一件有期限」是一張**圖**(entitlement graph),不是
一段文字。通用模型把項目並列,因為它不掌握項目之間的關係。

### 3. 說得出「不符合」

多條件組合正是通用模型最容易出錯的地方,而且出錯時語氣一樣肯定。

後果不是「答案品質不佳」,而是**一個剛失去家人的人抱著期待跑一趟機關,然後被退件**,
而他當下沒有心力承受這件事。

反過來,「你不符合,原因是差在這個條件,不需要白跑這一趟」是極有價值的資訊。通用
模型傾向於不把話說死,因為它被訓練成盡量 helpful。

我們的 rule engine 只輸出 `eligible` / `ineligible` / `needs_information` /
`needs_human_review` 四種狀態,`ineligible` 是一等公民。**這是最強的差異化,也最好演示。**

### 4. 可稽核的官方依據

給付條件與金額會調整,模型的知識有截止日,而使用者無法分辨它引用的是哪一年的規定。
更根本的是:即使答案正確,使用者也**無法驗證**。

這個領域的使用者需要能拿著結果去問承辦人。因此每一項判定都要附官方 URL、發布機關、
發布日期與適用版本。

注意:這一點單靠 RAG 就能達成,**所以它不足以單獨證明我們不是套皮**。它是必要條件,
不是充分條件。

## 判準:拿掉 LLM 之後還剩什麼

給團隊一個可以隨時自我檢查的定義:

> **套皮 = 把使用者的問題轉發給模型,把模型的回答轉發給使用者。程式碼裡沒有任何知識。**

接住有三樣資產屬於我們,不屬於模型:

1. **Entitlement graph** — 哪個人生事件牽動哪些福利與行政事項、彼此的先後順序、
   分屬哪個機關。這是人工 curate 的資料。
2. **Eligibility rules** — 以程式碼與結構化規則表達的判斷邏輯。可測試、可稽核,
   錯了可以改一行並補一個測試永久修好。
3. **驗證過的官方文件集** — 經過挑選、標註機關、日期與版本的來源。

**檢驗方式:把 LLM 整個移除,系統還能不能運作?**

接住的答案是「能」。使用者改用選單逐項點選,一樣會得到正確的資格判定、辦理順序與
官方依據,只是輸入體驗變差。套皮產品移除模型之後什麼都不剩。

這正是採用 policy-governed 架構([ADR-0003](decisions/0003-policy-governed-hybrid-orchestration.md))
的意義:**模型是輸入與輸出的介面,不是系統的大腦。**

## 定位推導出的產品決策

### 接住做導航,不做代辦

產出是「該辦什麼、什麼順序、要帶哪些文件、去哪個機關」,不是替使用者把申請書填好。

直接後果:

- **前端不保存姓名、身分證字號等 direct identifiers。** 資格判斷靠的是條件(關係、
  投保身分、年齡區間、是否扶養未成年子女),不是身分。使用者的識別資料在臨櫃時
  由本人填寫,系統從頭到尾不接觸。
- 因此可以主張「我們不需要、也不接收任何身分資料」,而且這句話守得住 —— 它來自
  產品定位,不只是隱私設計。相關的狀態邊界見
  [ADR-0005](decisions/0005-split-client-server-session-state.md)。
- 代辦、表單預填、跨機關線上送件都**不在 MVP 範圍**。它們會把時間從資格判斷與官方
  依據上拉走,而那兩者才是差異所在。

### 深度優先於廣度

MVP 鎖定單一情境並做到可稽核,勝過覆蓋十種情境但每種都只有模糊建議。廣度是通用
模型的主場,不要在那裡交戰。

## Demo 必須看得見的四件事

最大的風險不是做不出差異,而是**做出來了但看不見**。如果 demo 呈現為「輸入一段話 →
出現一份清單」,觀眾會直接把它歸類為聊天模型的包裝。

以下四項應該在畫面上明確出現:

1. 系統**反問**一個通用模型不會主動問的必要條件。
2. 判定結果旁邊有可點擊的官方依據連結,含發布機關與日期。
3. 出現一個 **`ineligible` 判定**,並指出差在哪一個條件。
4. 一張帶有**順序與期限**的辦理路徑,而非並列清單。

## 已知弱點與回應方式

**「你們只覆蓋少數福利,通用模型什麼都能回答。」**
屬實。我們的優勢是深度與可稽核性。擴展路徑是新增 entitlement graph 資料與規則,
屬於加資料而非改架構。

**「加一個好的 prompt 是不是就能做到一樣的事?」**
prompt 可以要求模型發問或引用來源,但無法保證它問完所有必要欄位、無法保證引用的
文件真實存在、也無法在判定錯誤時提供可修復的位置。我們把資格判定放在規則引擎,
是為了讓錯誤可定位、可測試、可永久修正。

**「目標使用者是長輩,他們本來就不會用聊天模型。」**
這是真的,但屬於介面問題,容易被回應為「那就把介面做好」。實務上實際操作的人往往
是代為處理的子女,而那個人會使用通用模型。因此這一點可以作為補充,**不應該當作
主要論據**。

## 如何使用這份文件

評估一個提案時依序問:

1. 它強化上述四個差異中的哪一個?
2. 移除 LLM 之後,這個功能還成立嗎?
3. 它是否需要我們開始接收 direct identifiers?若是,重新檢視是否偏離導航定位。
4. 它在 demo 上**看得見**嗎?

四題都答不出來的提案,優先級應該往後排。
