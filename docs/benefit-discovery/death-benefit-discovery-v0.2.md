# 親人過世補助探索規格 v0.2

## 這一輪要完成什麼

這一版只定義「系統要怎麼找候選資源」，尚未實際連線搜尋政府平台。

- 使用者介面名稱：親人過世
- 內部主題名稱：死亡、喪葬與遺族
- 第一輪地理範圍：中央政府與臺北市
- 主要範圍：補助、直接降低喪葬費用的政府服務及重要死亡／喪葬給付
- 次要範圍：遺屬後續生活支持
- 關鍵字：
  [`death_benefit_keywords.v0.2.json`](../../data/benefit_discovery/death_benefit_keywords.v0.2.json)
- 固定測試案例：
  [`death_benefit_discovery.v0.2.json`](../../data/evaluations/death_benefit_discovery.v0.2.json)

這份規格不會因為網頁命中關鍵字，就直接宣稱它是可申請的補助。關鍵字只負責把
可能有用的頁面放進候選區，正式收錄仍須核對官方證據。

## 第一輪收錄邊界

優先尋找：

- 喪葬、殮葬、安葬、火化、納骨等現金補助或費用補助。
- 公立殯葬設施費用免收、減徵或其他規費優惠。
- 聯合奠祭等由政府提供、可直接降低家屬喪葬支出的服務。
- 社會保險死亡或喪葬給付。
- 因死亡事實發給的一次性救助、慰問或補償。

可以發現但放在次要區：

- 遺屬年金、遺屬津貼及其他持續生活支持。
- 撫卹、犯罪被害補償等需要另外確認制度與適用情境的資源。

第一輪不收：

- 只有死亡登記、除戶或證件註銷的行政說明。
- 遺產稅喪葬費扣除額及一般繼承、稅務資訊。
- 私人殯葬商品、業者、廣告或民間募款。
- 鄉鎮市區自行加碼；等中央與臺北市流程跑通後再擴充。
- 以動物、家畜、家禽或寵物為資源主體的補助。

法規、新聞、統計、預決算及採購資料不能單獨成為一筆正式方案；其中法規或公告可以
保留為方案證據，新聞與統計則降低審查優先順序。

## 整個查詢流程

### 1. 先確認去哪裡找

搜尋器只能從已登記的來源開始，例如政府資料平台、我的 E 政府或已確認的政府機關
網站。來源登記至少要知道：

- 網域與機關。
- 是否為臺灣政府正式來源。
- 來源類型，例如福利入口、法規、新聞、統計或採購。
- 允許使用 API、檔案、網站索引或其他何種取得方式。
- 最後人工確認日期。

不認識的來源不會自動核准；它會停在待確認區。

### 2. 將文字整理成可以穩定比對的形式

保存原文後，另外建立搜尋用文字：

- 合併多餘空白及全形排版空白。
- 統一全形與半形括號供比對。
- 讓「臺／台」及「撫卹／撫恤」可對應同一個標準詞。
- 不把整頁簡體字自動轉成繁體；偵測到簡體只會阻止自動核准。

高精確完整詞先用整理後原文比對，再做一般斷詞與組合搜尋。

### 3. 用四種方式發現候選

第一種是完整名稱，例如：

```text
喪葬費補助
無力殮葬
死亡救助
國民年金喪葬給付
```

第二種是在同一個內容區塊內，同時找到喪葬服務詞與經濟協助詞，例如：

```text
火化場 + 免收
納骨塔 + 費用減免
殮葬 + 救助
```

第三種是在同一個內容區塊內，同時找到死亡事件詞與經濟協助詞，例如：

```text
身故 + 慰問金
死亡 + 補助
```

這一種較容易誤找，只能建立弱候選。

第四種是辨認福利清單、服務一覽或殯葬收費標準，展開它的子連結、表格列或清單項目，
再重新執行前述規則。

「補助」「免費」等單一廣泛詞不能自行建立候選。

### 4. 以內容區塊判斷，不用整頁湊字

政府頁面可能包含標題、表格、卡片、清單及頁尾。系統應以同一個有語意的內容區塊
比對，而不是在頁面開頭找到「死亡」、頁尾找到「補助」就算命中。

內容區塊可以是：

- 標題及緊接的說明。
- 表格中的同一列。
- 同一張服務卡片。
- 同一個清單項目。
- PDF 中的同一段或同一表格列。

### 5. 分流候選

候選不會全部混在一起：

| 候選區 | 例子 |
| --- | --- |
| 主要補助候選 | 喪葬費補助、無力殮葬急難救助 |
| 政府服務候選 | 聯合奠祭、免費或減免的殯葬服務 |
| 相關財務資源候選 | 喪葬給付、遺屬年金、撫卹、補償 |
| 收費資訊候選 | 公立殯葬設施收費標準，仍要確認是否真的有減免 |
| 弱候選 | 只命中「死亡＋補助」等寬鬆組合 |
| 來源待確認 | 非已登記來源或疑似非臺灣來源 |

同一區塊可能同時命中多條規則。這時先處理排除，再以完整詞決定專用候選區；例如
「喪葬津貼」即使也能拆成「喪葬＋津貼」，仍先進相關財務資源候選，而
「聯合奠祭＋免費」仍先進政府服務候選。系統會保留所有命中理由供審查。

### 6. 排除明確不相關的候選

可以自動排除的條件必須可記錄、可重跑：

- 來源登記已確認為非臺灣政府。
- 來源登記已確認為商業網站。
- 來源類型已確認為純採購平台。
- 該候選內容區塊明確以動物、畜禽或寵物為資源主體。
- URL 正規化後與既有候選重複；這種情況改做去重，不刪除原始證據。

動物規則只排除該內容區塊，不刪除整頁，避免一份災害文件同時包含人員與農業救助時
誤刪人員資源。

每次排除至少記錄：

```text
rule_id
candidate_block
matched_span
source_registry_id
decided_at
```

新聞、統計、研究、預決算及簡體字訊號只降低優先順序或阻止自動核准，不單獨硬刪。

### 7. 人工確認後才成為正式方案

審查者要確認：

- 是否真的存在可申請、請領、減免或使用的資源。
- 官方證據能否說明方案、申請方式及目前狀態。
- 資源是喪葬支出、一次性死亡支持，還是遺族持續生活支持。
- 制度依據是政府補助、社會救助、社會保險、撫卹或補償等哪一類。
- 實際提供現金、定期給付、核銷、費用減免或政府服務。
- 誰可以申請、期限從何時起算，以及是否不能和其他資源重複請領。

無法確認時保留 `uncertain`，不能推定有效。

### 8. 最後才連回政府機關 OID

方案完成證據審查後，才依官方資料建立主管、執行、受理及資料發布機關角色，再連回
OID registry。不能因為某機關發布資料，就推定它是補助主管機關。

## 方案分類欄位

`support_purpose` 回答資源用來幫什麼：

- `funeral_cost`：喪葬支出、費用減免或政府負擔的喪葬服務。
- `one_time_death_support`：因死亡事實一次發給，不限定喪葬支出。
- `survivor_livelihood`：遺族後續持續生活支持。

`program_basis` 回答資源屬於哪種制度：

- `government_subsidy_or_relief`
- `social_assistance`
- `social_insurance`
- `survivor_pension_or_pension`
- `legal_compensation`
- `employer_statutory_payment`
- `other_or_unknown`

`delivery_form` 回答使用者實際得到什麼：

- `cash_once`
- `cash_recurring`
- `reimbursement`
- `fee_waiver`
- `service_or_in_kind`
- `unknown`

使用者畫面可由 `support_purpose` 分成：

```text
funeral_cost 或 one_time_death_support
→ 親人過世後優先處理

survivor_livelihood
→ 遺族後續生活支持
```

不另存可自由填寫的 `relevance`，避免分類彼此矛盾。

## 重要審查資訊

第一版至少保存原始文字與證據：

- `expense_proof_requirement`：
  `required`、`not_required`、`conditional` 或 `unknown`。
- `claimant_rule_text`：誰可以申請或請領。
- `deadline_rule_text`：期限與起算事件的官方原文。
- `mutual_exclusion_text`：不得重複請領或會互相影響的官方原文。
- 每一項資訊的官方 URL、原文片段、取得日期與人工審查狀態。

這些文字日後才能轉成確定性資格規則；LLM 不得只依關鍵字自行判定使用者符合資格。

## 這一輪不代表什麼

- 尚未搜尋政府資料平台、我的 E 政府或任何機關網站。
- 尚未確認任何方案目前可申請。
- 尚未修改 SQLite 或建立正式方案資料表。
- 尚未承諾涵蓋全臺所有縣市、鄉鎮市區或 7,988 個機關。
- 尚未實作搜尋器、網頁解析器或自動分類器。

下一輪應挑選一個正式來源，把固定測試案例轉成可執行測試，再用少量真實頁面測量
漏找、誤找與待人工確認的數量。
