1. 這個分支解決了什麼問題

在這個分支之前，前端和後端沒有辦法一起開發。原因是兩邊沒有講好要傳什麼資料。

前端工程師不知道後端會回什麼欄位，只能自己寫死假資料；後端工程師不知道前端需要什麼， 只能猜。兩邊各做各的，最後接起來一定會壞。

這個分支做了三件事：

做了什麼解決什麼
定義後端內部的狀態形狀 後端自己知道「一次諮詢」要記住哪些東西
定義前後端之間的資料契約 兩邊可以同時開發，而且改壞了會被測試抓到
做出可以真的呼叫的 API 端點 前端可以開始接，拿到的是真實形狀的回應
但功能還沒有。 端點回的資料是寫死的：不管使用者輸入什麼，事件都判定成「配偶過世」， 候選項目固定四個，沒有任何資格判定。這是刻意的 —— 目標是「形狀對了」，不是「功能好了」。

2. 整個系統的架構

先看全貌，這樣才知道這個分支在哪個位置。

┌─────────────────────────────────────────────────────────┐ │ 瀏覽器（React） │ │ 使用者打字、選答案、看結果 │ │ 姓名、身分證等個資只留在這裡，不往後送 │ └─────────────────────────────────────────────────────────┘ ↕ HTTP，JSON ┌─────────────────────────────────────────────────────────┐ │ API 層（FastAPI） ← 這個分支做的 │ │ 只做收發與驗證，不放商業邏輯 │ └─────────────────────────────────────────────────────────┘ ↓ ┌─────────────────────────────────────────────────────────┐ │ 流程控制層（state machine） ← 這個分支只做了臨時替代品 │ │ 決定現在該問什麼、能不能往下一步、什麼時候該找人 │ └─────────────────────────────────────────────────────────┘ ↓ ↓ ↓ ↓ ┌─────────┐ ┌───────────┐ ┌──────────┐ ┌────────┐ │ LLM │ │ 規則引擎 │ │ 官方文件 │ │ 隱私 │ │ 聽懂人話 │ │ 判斷資格 │ │ 檢索 │ │ 閘門 │ │ 講白話 │ │（不用 AI） │ │ │ │ │ └─────────┘ └───────────┘ └──────────┘ └────────┘ ↓ ┌──────────────────┐ │ 本機 SQLite │ │ 補助方案、官方依據 │ └──────────────────┘

最重要的一條原則

AI 不決定資格。 LLM 只做兩件事：把使用者的話變成一個分類代號，以及把已經決定好的結果翻成白話。

「符不符合資格」由規則引擎決定 —— 那是寫死的判斷邏輯， 同樣的輸入永遠給同樣的答案。這種特性叫 deterministic（確定性）， 意思是可驗證、可解釋、不會亂。

這條原則是整個專案的核心主張，也寫進了架構決策紀錄（ADR-0003）。 把 LLM 整個拿掉，系統仍然能判斷資格，只是使用者要改用選單輸入。

八個流程步驟

一次諮詢固定走這八步。每一步的名稱在程式裡是 WorkflowState 這個列舉。

步驟做什麼誰在決定
understand_event聽懂發生了什麼事，等使用者確認LLM 提議，使用者拍板
resolve_entitlements展開可能相關的項目資料查表
collect_missing_fields按主題逐組追問規則算出缺什麼
retrieve_rules檢索官方依據檢索模組
evaluate_eligibility判定資格規則引擎
explain_result補上白話說明LLM
confirm複查答案、詢問轉介使用者
complete產生有順序的辦理清單資料查表

中間第 3、4、5 步會形成一個迴圈：使用者答完一組問題， 後端就檢查有沒有項目湊齊條件、湊齊的當場判定，還缺的繼續問。 這樣結果會一項一項出現，而不是全部等到最後。

迴圈需要護欄，否則可能轉不出來。目前規劃了四道：檢索先行、最多繞 6 圈、 每圈必須有進展、已定案的項目不重跑。這些還沒實作。

5.2 每一層的責任與禁止事項

「禁止事項」那一欄比「責任」那一欄更重要 —— 它是這個架構能不能撐住的關鍵。

層責任禁止
api/ 讀 header、驗證請求格式、呼叫下一層、把結果轉成回應、把錯誤轉成狀態碼 不做任何流程判斷。不能出現「如果現在是第三步就…」這種程式
schemas/ 定義前端看得到的形狀；驗證外部輸入 不含邏輯。不直接建立內部狀態物件
orchestration/ 擁有狀態、決定能不能往下一步、管迴圈與重試、決定哪些工具現在可以用 不判斷資格。不直接讀資料庫、不直接呼叫模型
rules/ 吃屬性吐四種結論，並指出決定性條件 不呼叫 LLM。不知道流程走到哪一步。不決定要問什麼問題
retrieval/ 找出官方依據，組出引用 不判斷資格。不改寫文件內容
privacy/ 擋掉不該進來的欄位、丟棄原文 不做業務判斷
services/ 跟外部世界（資料庫、網頁、未來的 AWS）打交道 不含業務規則
observability/ 記錄發生了什麼 不接受使用者輸入的值，程式層強制

三條禁止事項是整個專案的主張，不是風格偏好

  • api/ 不做流程判斷 —— 否則流程規則會散在路由裡， 無法單獨測試，也無法回答「這個狀態轉換合法嗎」
  • orchestration/ 不判斷資格 —— 這是 ADR-0003 的核心。 資格判定必須集中在一個確定性的地方，才能對評審和使用者解釋
  • rules/ 不呼叫 LLM —— 這是「AI 不決定你符不符合資格」 這句話的實際落實方式

5.3 誰可以 import 誰

依賴方向決定了改一個檔案會影響多少東西。箭頭代表「可以 import」。

api/ ────────────────┐ │ │ ↓ ↓ schemas/ ────────→ orchestration/ │ ↓ rules/ retrieval/ services/ │ ↓ observability/ ← 任何一層都可以用

規則是：箭頭只能往下，不能往上。

  • api/ 可以用 schemas/ 和 orchestration/
  • orchestration/ 不能 import api/ —— 否則流程邏輯就跟 HTTP 綁在一起，換掉 web 框架就要重寫
  • rules/ 不能 import orchestration/ —— 規則不該知道現在走到第幾步
  • observability/ 是例外，任何一層都可以用它記錄

目前有一個違反這個規則的地方，要誠實說明

orchestration/mock_advance.py import 了 schemas/session.py，也就是流程層依賴了傳輸層。 按上面的規則，箭頭方向錯了。

原因是七種輸入形狀（LifeEventTextInput 等）定義在 schemas/ 裡，而推進邏輯需要判斷「這次送來的是哪一種輸入」。

正確的做法是把「輸入的種類」定義在 orchestration/， 讓 schemas/ 去投影它 —— 跟回應那一側的做法一致 （SessionSnapshot 是 SessionState 的投影）。

這件事留到實作真正的 state machine 時一起處理，因為那時 mock_advance.py 會整個刪除。但不要在新程式裡沿用這個寫法。

5.4 一次請求從頭到尾發生什麼

以 POST /sessions/advance 為例，這是最完整的一條路徑。 下面每一步都對得上實際的程式。

1. 前端發出請求 POST /sessions/advance Header: X-Session-Id: <隨機字串> Body: {"input": {"kind": "attribute_answers", "answers": {...}}} ↓ 2. FastAPI 驗證請求本體 schemas/session.py 看 kind 的值決定要用哪一種形狀來驗 格式不符 → 跳到步驟 9（錯誤處理） ↓ 3. 取出 session api/sessions.py 從 header 讀 X-Session-Id 沒帶 → 401 session_not_found 找不到 → 404 session_not_found 已過期 → 410 session_expired，並刪除該筆 ↓ 4. 推進一步 orchestration/mock_advance.py （未來會是 state_machine.py） 不合法的動作 → 409 invalid_transition 項目代號不存在 → 422 unknown_item → 產生一個「新的」狀態物件，不修改舊的 ↓ 5. 寫回 orchestration/session_store.py 替換儲存的狀態、蓋上 updated_at 注意：不延長 expires_at ↓ 6. 記錄 observability/logging.py 只記狀態名稱、事件代號、項目數量 使用者提供的值傳不進去，會直接報錯 ↓ 7. 組出回應 schemas/session.py 從內部狀態投影出對外快照 丟掉 loop_iterations、rule_id 等內部欄位 附上「哪些能力還沒實作」的說明 ↓ 8. 輸出 JSON 欄位名轉成 camelCase 回 200 ↓ 9. 若中途出錯 api/errors.py 轉成 {errorCode, fieldIds, currentState} 驗證錯誤只留欄位路徑，訊息與原值一律丟棄

三個值得注意的設計

步驟 4 產生新物件而不是修改舊的。 因為狀態物件設成 frozen，改欄位會直接報錯。所以「誰改了狀態」永遠追得到 —— 只有這一步會產生新狀態。

步驟 5 不延長過期時間。 使用者一直在操作也不會延長那 2 小時。保存上限從建立時算起， 這是對使用者的承諾，不是閒置逾時。

步驟 7 是投影而不是照搬。 內部有 13 個欄位，對外只露出前端需要的。這樣之後想改內部欄位名稱或移除某個計數， 不會變成改 API。

5.5 應用程式怎麼組起來

main.py 只做四件事，每一件都刻意做得很薄：

def create_app() -> FastAPI:
    configure_logging()                              # 1 裝上 JSON 格式的記錄器
    settings = get_settings()                        # 2 讀環境變數
    app = FastAPI(...)
    app.add_middleware(CORSMiddleware, ...)          #   允許前端跨來源呼叫
    app.state.session_store = InMemorySessionStore() # 3 建立 session 儲存
    install_error_handlers(app)                      # 4 裝上錯誤轉換
    app.include_router(health_router)
    app.include_router(sessions_router)
    return app

app = create_app()
設計為什麼
用一個函式建立應用程式（factory） 測試可以建出互相隔離的實例。14 個端點測試各自有自己的 session 儲存， 不會互相污染
session 儲存掛在 app.state 不用模組層級的全域變數。要換成 DynamoDB 時只改這一行
CORS 沒有開 allow_credentials 因為 session id 不用 cookie，走 header。不開等於少一條被攻擊的路徑
加端點只要多一行 include_router 新增功能不需要改這個檔案的其他部分

5.6 三個貫穿全域的機制

一、記錄的欄位允許清單

observability/logging.py 的 log_event 只接受清單上的欄位名稱，其他直接丟出錯誤。

清單裡的欄位分成八組，全部是代號、名稱、計數、結果：

關聯
session_id、request_id
流程
state、next_state、transition、guard
Agent
tool、tool_allowed、agent_iterations、model_id
項目
candidate_count
規則
rule_id、rule_version、eligibility_status…
檢索
document_id、source_count
欄位名稱
missing_field_names、extracted_field_names、life_event
結果
outcome、status_code、duration_ms、error_type

沒有任何欄位可以放「使用者填的值」。 所以寫 log_event("x", text=使用者的話) 會立刻報錯， 而不是默默記進去。

二、狀態不可修改

所有狀態物件都設 frozen=True，改欄位會報錯。要改就用 model_copy(update={...}) 產生新物件。

再加上 extra="forbid"：出現沒定義的欄位也報錯，所以打錯欄位名會被抓到。

一個要誠實說明的限制：frozen 只擋「換掉整個欄位」， 不擋「修改欄位指向的那個物件」。attributes 是一個 dict， 所以 state.attributes["x"] = 1 在執行時仍然會成功。 序列型的欄位都改用不可變的 tuple，但那個 dict 保留了 —— 請當成唯讀。

三、錯誤一律轉換過才對外

api/errors.py 攔下兩種東西：我們自己拋出的 ApiError，以及 FastAPI 的驗證錯誤。

第二種是重點。Pydantic 驗證失敗時，錯誤訊息會把不合法的值原文引用進去。 直接回傳等於把使用者打的字送回去，而且任何記錄這個回應的地方都會留下它。

處理方式是只取出欄位路徑（例如 input.life_event_text.text），訊息與原值一律丟棄。

6. 四個核心概念

這四個名詞在程式和文件裡到處出現，先弄懂會省很多時間。

概念一：SessionState（諮詢狀態）

一次諮詢的完整紀錄，13 個欄位。放在 state.py。

session_id隨機編號，跟身分無關
workflow_state目前走到八步中的哪一步
life_event事件代號，例如 spouse_death
attributes使用者答過的條件
items候選項目與各自的結果
loop_iterations迴圈繞了幾圈（護欄用）
event_retry_count使用者說「不是這樣」幾次
exit_reason提前結束的原因
referral_requested是否要求轉介
is_processing是否還在處理中（給前端輪詢判斷）
created_at / updated_at / expires_at三個時間

它有兩個特殊設定

frozen=True：建立之後不能改欄位。要改就產生一個新物件。 這樣做的好處是「誰改了狀態」永遠追得到 —— 所有變化都必須經過流程控制那個檔案， 程式其他地方改不了。

extra="forbid"：出現沒定義的欄位就直接報錯。 這樣手滑打錯欄位名會立刻被發現，而不是默默被忽略。

概念二：CandidateItem（候選項目）

第 3 步展開的每一件事就是一個候選項目。目前 MVP 情境有四個：死亡登記、喪葬給付、 遺屬年金、健保身分變更。

每個項目各自帶一個狀態，所以同時有好幾項符合是正常情況。

狀態意思誰能設定
pending待確認，還在等欄位初始值
eligible符合規則引擎
ineligible不符合，必須指出差在哪個條件規則引擎
needs_information資訊不足規則引擎
needs_human_review需人工協助規則引擎
declined_by_user使用者說不想辦使用者

程式裡有一個常數 RULE_ENGINE_STATUSES 列出中間那四個。 規則引擎回傳 pending 或 declined_by_user 一定是 bug， 呼叫端應該拒絕 —— 因為規則引擎擁有「判定」，但不擁有「項目的生命週期」。

項目還帶四個金額欄位（最低、最高、發放性質、幣別）。 刻意不放已排版的文字，例如「10,000 元」—— 那屬於前端，見下一個概念。

概念三：後端給代號，前端給文字

這是貫穿整個契約的一條分界線。

後端回傳的是代號：spouse_death、funeral_benefit、 eligible、session_expired。

畫面上給人看的文字全部由前端提供：「配偶過世」、「喪葬給付」、 「你符合」、「進度已過期」。

為什麼這樣分

  • 加一個新的資格欄位時，只要前端補一段文案，不用改後端邏輯
  • 這個產品的使用者正在人生低谷，用字很重要，那是負責使用體驗的人的專業
  • 後端專注在「該說什麼」，前端專注在「怎麼說」
目前有一個刻意的例外。 回應裡有一個 placeholderNotice 欄位，內容是中文的 「（此為後端傳來的暫時資料…）」。這違反上面的分界，但它的讀者是開發者和 demo 觀眾， 不是真正的使用者。佔位資料移除時它會一起刪除。

概念四：決定性條件（decisive condition）

這是整個專案最重要的差異點，值得單獨講。

一般的系統告訴你「不符合資格」。這個專案要求說得出是哪一個條件造成的： 

差在這個條件：投保年資
你的情況：5 到 15 年   ／   需要：15 年以上

所以每個判定結果都帶一個結構，三個部分：

field_id
是哪個條件
expected
規則要求什麼
actual
使用者的情況是什麼

而且是強制的：如果規則說不出「不符合」是差在哪， 就不准輸出「不符合」，要降級成「需人工協助」。 說不出原因的拒絕，比不回答更傷人。

這一項目前接不起來。 資料層的規則引擎回的是一串中文句子（例如「需設籍該縣市」），不是三段結構。 我們的形狀準備好了，但需要規則引擎那側配合輸出。詳見第 7 節。

7. 跟前端怎麼互通

四個端點

方法路徑用途成功碼
POST/sessions建立諮詢，回應含 sessionId201
POST/sessions/advance送一筆輸入，推進一步200
GET/sessions/current查目前狀態（輪詢用）200
DELETE/sessions/current立刻清除204

為什麼 id 走 header 而不是網址

除了建立之外，每次呼叫都要帶 X-Session-Id 這個 header。

原因是 session_id 同時扮演「是誰」和「證明是本人」兩個角色 —— 沒有帳號密碼再驗一次，誰拿到就能讀到那份狀態。 這種憑證在安全上叫 bearer token（持有即通行）。

如果放在網址裡，它會出現在這些地方：瀏覽器的瀏覽記錄、伺服器的存取日誌、 使用者點外部連結時傳給對方的 referrer、使用者複製網址貼給別人時。

走 header 就不會經過這些路徑。代價是用瀏覽器直接貼網址測試比較麻煩。

七種輸入

推進的請求本體是 {"input": {"kind": ..., ...}}。 kind 決定其餘欄位長什麼樣。這種設計叫 discriminated union（可辨識聯集）。

kind對應畫面其餘欄位
life_event_text描述事件text
event_confirmation確認理解confirmed
attribute_answers送一組答案 / 修正answers
item_decline「這一項我不想辦」itemId
review_confirmation確認產生清單confirmed
referral_choice要不要轉介requested
help_request要求人工協助無
life_event_text 是唯一帶文字的形狀。 其他六種在型別上就沒有文字欄位，所以自由文字不可能出現在後面的步驟。 這不是靠檢查擋，是結構上不存在。

回應的形狀

三個端點都回同一個 SessionSnapshot。它是內部狀態的投影—— 只挑出前端需要的部分，不照搬全部。

不露出的內部欄位為什麼
loop_iterations、event_retry_count護欄用的計數，露出去會被誤用
updated_at畫面上沒用到
rule_id、rule_version給我們追查用的，露出等於把規則編號變成對外承諾

兩個現在一定是固定值的欄位

  • questionGroups 一定是空陣列，因為問題卡需要欄位登記表，那還不存在
  • isProcessing 永遠是 false，因為目前是同步處理，一次呼叫做完才回

欄位命名：線上是 camelCase

Python 的慣例是 item_id，TypeScript 的慣例是 itemId。 我們讓網路上傳的 JSON 用 camelCase，Python 程式內部維持 snake_case。 兩種語言各自維持慣例，前端不用自己轉換。

但列舉的值不變：needs_information 還是 needs_information，因為那是資料內容不是欄位名稱。

錯誤的形狀

{ "errorCode": "session_expired", "fieldIds": [], "currentState": "collect_missing_fields" }
errorCodeHTTP什麼情況
session_not_found404 / 401找不到，或沒帶 header
session_expired410超過 2 小時
unknown_field422欄位不在登記表上
invalid_field_value422值不符合型別
unknown_item422項目代號不存在
invalid_transition409目前狀態不允許這個動作
internal_error500後端自身錯誤

三個欄位都不能放值 —— 代號、欄位名稱、狀態名稱。 所以這個形狀在結構上不可能洩漏使用者輸入。理由見第 8 節。

兩份契約怎麼保持同步

契約兩邊手寫（Python 和 TypeScript），最大的風險是改了一邊忘了另一邊。

所以有一個測試會直接讀取前端的 session.ts 這個檔案， 用文字比對欄位名稱、列舉的值、以及文字長度上限。不一致就讓測試失敗，並指出是哪個形狀。

8. 跟資料層怎麼互通

資料層負責回答「世界上有哪些補助、條件是什麼、依據在哪」。 它已經做了不少東西：政府機關資料、官方頁面下載、補助方案 catalog、 一個通用規則引擎，還有相關性評分。

目前還沒有接起來

這個分支完全沒有呼叫資料層。端點回的是寫死的資料。 接上是後續任務。

接上的方式：三個介面，不直接寫 SQL

介面問什麼
Entitlement graph這個事件牽動哪些項目？順序與依賴是什麼？
規則來源這個項目的判斷條件是什麼？
官方依據檢索這個項目的依據是哪些文件、哪一段？

分成三個而不是一個的理由：如果只有一個「資料層」介面， 規則判定就有機會直接去撈文件內容，兩者糾纏之後就沒辦法單獨測試規則了。

五個形狀落差

兩邊的資料形狀還沒對齊。完整內容維護在 docs/back_database_doc/README.md，這裡只列摘要。

落差狀況
金額：規則引擎回單一數字，我們需要上下界與發放性質 形狀已補，轉接未做
決定性條件：規則引擎回中文句子，我們需要三段結構 需資料層配合
相關性評分：規則引擎會算分排序，我們沒有欄位接 待決定
命名：program_id 對 item_id 等 後端寫轉接
隱私：規則引擎的說明字串裡混入了使用者提供的值 需資料層配合
第五項要特別注意。 規則引擎有這樣的寫法：f"不適用此骨灰骸類型: {user_type}"。 那個 user_type 是使用者提供的值，混進了一個字串裡。 目前不會漏（那個欄位不在紀錄檔的允許清單裡）， 但如果未來有人為了除錯把它加進清單，就沒有人會記得裡面混著使用者的值。

屬性名稱的詞彙已經存在了

規則引擎已經在讀這些屬性名稱：registered_in_city、 remains_type、deceased_status、 eco_burial_completed。

所以之後做欄位登記表時，應該沿用這些名稱， 不要另外發明一套再寫轉換。

9. 隱私是怎麼用程式強制的

這個專案把隱私當成主要主張，所以不能只寫在文件裡。以下五道防線裡， 這個分支負責的是第三、四、五道。

防線做法狀態
1. 不需要身分資料產品只做導航不做代辦，本來就不需要姓名身分證達成
2. 送出前在瀏覽器遮罩偵測身分證、電話、email 格式未做
3. 後端不保留原文抽取完屬性後丟棄結構已擋
4. 屬性要在允許清單上不在清單的欄位整筆拒絕未做
5. 紀錄檔連寫的機會都沒有只接受允許清單上的欄位名稱完成

為什麼要五道

因為第二道必然會漏。身分證、電話、email 有固定格式可以偵測， 但中文姓名沒有格式特徵 —— 「陳小明」和任何三個字在程式看起來一樣， 「王先生」「我家老李」更抓不到。

這不是實作品質問題，是原理上做不到。所以真正撐住主張的是第一道和第三道 —— 那兩道是結構性的（資料不存在／欄位不存在）， 而第二、四道是偵測性的（要判斷、會判斷錯）。

這個分支做到的三件具體事情

一、狀態裡沒有任何欄位可以放文字

SessionState 沒有 text、description、 raw_input、note，也沒有姓名、電話、email 的欄位。

而且有一個測試會掃過所有欄位名稱，出現這類字眼就失敗。 正當的例外（例如 Citation.publisher_name 是機關名稱，不是個人） 在測試裡逐一列名並附理由，所以放寬檢查必須是一次明確的修改。

二、自由文字在型別上只存在第一步

七種輸入形狀裡只有 life_event_text 有文字欄位。 在第五步想塞文字進去，Pydantic 會直接拒絕。

三、錯誤訊息不外洩原值

這一點值得詳細說明，因為它是一個很容易踩到的坑。

Pydantic 驗證失敗時，錯誤訊息會把不合法的值原文引用進去。 例如使用者打了一段 3000 字的話（超過 2000 字上限），預設的錯誤回應就會把那整段送回去。

更糟的是，任何記錄這個回應的地方都會留下它 —— 而那正是我們說「抽取後就丟棄」的東西。

所以有一個檔案 app/api/errors.py 專門處理這件事：

  • 攔下所有驗證錯誤，只取出欄位路徑，例如 input.life_event_text.text
  • 訊息和原值一律丟棄
  • 回應的形狀裡沒有任何欄位可以放值

有一個測試專門驗證這件事：送一段超長的中文進去，然後檢查回應裡查不到那些字。

同樣的原則早就寫進紀錄檔模組了。 app/observability/logging.py 只允許清單上的欄位名稱， 傳別的直接報錯。它甚至刻意只記錄例外的類別名稱而不記錄訊息， 並且用 format_tb 而不是 format_exception 來輸出堆疊 —— 因為後者會把訊息一起印出來。

11. 你必須知道的坑

坑一：完整測試套件在 backend/ 目錄下跑不起來

backend/README.md 寫的 uv run pytest（不指定檔案） 會在收集階段失敗，四個模組報 ModuleNotFoundError: No module named 'backend'。

原因是資料層的測試用的 import 路徑是從 repository 根目錄算起的 （from backend.app.services...）， 而 backend/pyproject.toml 設定以 backend/ 為根，兩者對不上。

暫時做法：明確指定要跑的測試檔案，像上面那樣。

坑二：Windows 上有 7 個資料層測試會失敗

從根目錄執行 backend/.venv/Scripts/python.exe -m pytest backend/tests 可以繞過坑一，但會有 7 個失敗，錯誤是 PermissionError: The process cannot access the file。

原因是資料層到處用 with sqlite3.connect(...) as connection:。 Python 的 sqlite3 用 with 包起來只會提交交易，不會關閉連線。 macOS 和 Linux 允許刪除還開著的檔案，Windows 不允許，所以測試的暫存目錄清不掉。

這不只是測試問題 —— 長時間執行的伺服器沿用同樣寫法會累積不釋放的連線。

坑三：舊的 uvicorn 行程會佔著埠，讓你以為程式壞了

這個坑實際踩到過，浪費了不少時間。症狀是：新的端點沒有出現在 /docs，看起來像 router 沒掛上。

實際原因是有一個舊的 uvicorn 行程還在跑，載入的是還沒有那些端點的程式， 並且佔著 8000 埠。而它的父行程已經死了，子行程繼承了監聽權， 所以查詢 owner 會看到一個「找不到的 PID」。

--reload 不會救你，因為問題不是「檔案沒重載」而是「舊行程還活著」。

診斷方式：

Get-CimInstance Win32_Process -Filter "Name='python.exe'" |
  Select-Object ProcessId, CreationDate, CommandLine | Format-List

看 CreationDate。如果比你今天開始寫程式的時間還早，就是它。 用 Stop-Process -Id <PID> -Force 殺掉。

坑四：PowerShell 的紅字不一定代表程式壞了

Invoke-RestMethod 遇到 4xx 或 5xx 會拋出例外，用紅字印一大段。 要看裡面那個 JSON —— 例如 {"errorCode":"invalid_transition","currentState":"resolve_entitlements"} 表示後端正確地拒絕了一個不該接受的請求。

另外，貼指令時不要連 PS D:\...> 一起複製， PowerShell 會把它當指令解析，噴出一堆 parse error。

坑五：ADR 編號會撞

不同分支各自新增架構決策紀錄時，很容易撞到同一個編號。 這個專案已經發生過一次：兩個分支各自寫了 ADR-0008，合併時才發現。

合併前先看 docs/decisions/ 目前最大的編號，並檢查其他未合併分支。

坑六：對外欄位是 camelCase，但列舉的值不是

itemId 是 camelCase，但 needs_information 保持 snake_case。 前者是欄位名稱，後者是資料內容。改的時候不要一起換。

順序要做什麼為什麼排這裡
