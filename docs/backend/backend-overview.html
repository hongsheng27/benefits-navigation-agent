最後更新：2026-07-30 ｜ 分支：feat/backend-llm-port ｜ 延續 專案架構與資料庫說明

這一層在做什麼？

資料層已經回答了「世界上有哪些補助、條件是什麼、依據在哪」。 這一層要回答的是另一個問題：「面對眼前這一個人，接下來要做什麼」。

兩者的差別是：資料層處理的是方案，這一層處理的是一次對話。 同一個人可能同時符合三項、有一項還缺資料、有一項不符合，而且他答到一半可能會離開再回來。 這些都是這一層的責任。

分工界線：資料層決定「條件是什麼」，Rule Engine 決定「符不符合」， Workflow 層決定「現在該問什麼、能不能往下一步、什麼時候該停下來找人」。 Workflow 層不判斷資格。

為什麼要有 [1] 那個「等使用者確認」

這是整條流程裡 LLM 唯一有機會讓後面七步全錯的地方。如果它把「我先生過世」誤判成別的事件， 後面展開的項目、追問的欄位、判定的結果全部都是錯的。

讓使用者花兩秒點一下「對，繼續」，換掉一個系統性風險。

為什麼 [3] 的問題要按「主題」分組，不按「項目」分組

同一個欄位常常同時被多個項目需要。例如過世者的投保身分同時決定喪葬給付和遺屬年金。

如果按項目分組追問，使用者會被問兩次同樣的問題。對一個剛失去家人的人來說那不只是麻煩。

隱私邊界

這條界線來自產品定位，不只是隱私設計。接住做導航、不做代辦，所以本來就不需要身分資料。

內容
留在使用者裝置姓名、身分證字號、地址、電話、email、所有畫面文案
後端永遠不會有任何直接識別資料；自由文字原文（抽取完即丟棄）
後端保存（2 小時內）隨機編號、事件代號、去識別化屬性、缺漏欄位、項目代號、判定結果、規則版本、官方依據
紀錄檔只寫狀態、狀態轉換、工具名稱、規則代號、欄位名稱、計數、判定結果、耗時、錯誤型別

這兩條規則是用結構強制的，不是靠自律

  • SessionState 沒有任何欄位可以存放使用者打的字。沒有 text、description、raw_input、note。
  • extra="forbid" 會拒絕未知欄位，所以手滑加一個欄位會直接報錯。
  • 有一個單元測試掃描所有欄位名稱，出現代表文字或身分資料的片段就失敗。正當的例外在測試裡逐一列名並附理由。
  • log_event 只接受 allowlist 裡的欄位，傳別的直接拋錯。它刻意只記錄例外的類別名稱，因為例外訊息會引用不合法的原始值。
  • 欄位代號與欄位值有兩道獨立的檢查，兩道都拒絕整筆。代號不在登記表上，狀態機的 _record_answers 會拋 UnknownFieldError；值的型別或選項不符，RegistryBackedPrivacyGate 會拋 InvalidAttributeValueError。兩者都只回欄位代號，不回值。

最後那一條為什麼要拒絕整筆，而不是收下對的、退回錯的：如果部分接受，前端送三個欄位、 後端收了兩個，畫面上沒有任何地方能表達「有一個沒收到」，使用者會以為都填好了。

也為什麼要擋值而不只擋代號：只擋代號的話，送一個合法的代號配一段自由文字 （例如 deceased_insurance_type 配一整段個人敘述）就會通過， 然後那段文字會被存進 state 再原值回到前端。那正是 ADR-0007 要防的事。

Session 生命週期

建立使用者送出第一段文字時產生，隨機且足夠長
保存2 小時後自動過期
還原回訪時詢問「7/26 15:30 開始的諮詢，進度 3/8，要繼續嗎？」刻意不顯示事件類別，避免共用電腦洩漏
清除三個時機：開始時選擇不保留、全程常駐的清除按鈕、完成畫面詢問

不在關閉頁面時詢問，因為瀏覽器只允許顯示制式對話框、文字無法自訂、手機常直接忽略、 直接關機也不會觸發。做成「有時有、有時沒有」比不做更糟。

三件實測才知道、寫在這裡避免有人照舊教學重做一次的事。
  1. generateContent + responseSchema 那條路不能用。 它會回 400，因為那個 schema 型別不支援 additionalProperties， 而我們的可攜性規則要求它必須是 false（Bedrock 的硬性要求）。 兩者無法同時滿足，所以走 interactions 端點不只是「比較新」， 是唯一能同時滿足兩邊的路。
  2. generation_config 的欄位名是 snake_case。 送 maxOutputTokens 會被拒絕。這個 API 會拒絕未知欄位， 所以拼錯不會被默默忽略。
  3. 模型會把 JSON 包在 Markdown 圍籬裡，即使指定了 mime_type: application/json。adapter 會拿掉圍籬，但刻意只做 這件事 —— 不做「從一段文字裡挖出看起來像 JSON 的部分」， 那會把「模型答錯了」硬掰成成功。
測試不會用到真實模型，即使本機設了金鑰。 backend/tests/conftest.py 有一個 autouse fixture 把金鑰清成空的。 沒有它的話整套測試會真的打網路 —— 實測症狀是從 3 秒變成 46 秒、七個失敗。 三個理由：會花額度、會不穩（間歇性失敗的測試最後都會被關掉）、 以及結果取決於誰在跑。
為什麼不做 agent 迴圈。 系統裡只有兩個 LLM 工作（聽懂事件、翻成白話），兩個都是問一次答一次， 中間的檢索與判定是確定性的。而讓模型能自己呼叫工具，等於開出一條它可以影響資格判定 的路 —— 那是 ADR-0003 明文禁止的事。不存在的能力不需要防守。 ADR-0004 本身也允許單次結構化任務直接呼叫，所以這不是推翻它。
寫 schema 的硬規則：只用 Bedrock 支援的 JSON Schema 子集。 即使目前只接 Gemini 也一樣。不可用的有 minimum／maximum、minLength／maxLength、 遞迴 schema、外部 $ref，而 additionalProperties 必須明寫為 false。enum 可用，那正是我們需要的。

寫出 Gemini 接受但 Bedrock 拒絕的 schema，會在切換那天變成 400 錯誤， 而且每一份 schema 都要同時重新設計。

三條用結構強制的規則：模型回來的屬性走與使用者送答案相同的隱私閘門、 原文送出去但不寫 state 也不寫紀錄檔、解釋任務的回傳型別只有文字沒有 status 欄位所以改不了結論。另外刻意不做多輪對話 —— 沒有歷史就沒有歷史存在哪裡的問題。

失敗行為刻意不對稱：聽懂事件失敗不准猜（猜錯後面七步全錯）， 請使用者從清單挑或轉人工；白話解釋失敗照樣顯示結果， 只是沒有說明（說明是附加的，不能因為它壞掉就不給結果）。

跟 Rule Engine 與資料層之間的落差

backend/app/rules/engine.py 已經能讀 program_rule_fields 並回傳 EligibilityResult。它的四種狀態跟 workflow 層一致，但其餘形狀還沒對齊。

落差的完整內容維護在 docs/back_database_doc/README.md， 那是後端與資料層的溝通紀錄，包含各項的狀態與待確認事項。 這裡只列標題，避免兩份文件各自演進之後對不上。
落差狀態
金額：Rule Engine 回單一 amount，workflow 層要上下界與發放性質轉接已做，amount_period 仍缺
reasons 是文字，workflow 層需要「哪個欄位、要求什麼、實際什麼」三段結構需資料層配合
欄位命名不一致（program_id 對 item_id 等）轉接已完成
reasons 的字串裡混入使用者提供的值，寫進紀錄檔會洩漏需資料層配合
相關性評分：Rule Engine 會算分並排序，workflow 層沒有欄位接，也沒有說明順序依據未決，要不要露給前端
沒有存福利前後順序的表（entitlement graph 的節點與邊）需資料層配合，最擋人
規則條件用的屬性代號，欄位登記表上一個都沒有接 SQLite 前必須解決
最後那一項是 2026-07-30 新發現的，值得單獨說明。 規則引擎要求的屬性代號（remains_type、registered_in_city 等） 來自資料庫裡的條件字串；欄位登記表上的三個代號 （deceased_insurance_type 等）完全不一樣，交集是零。 而登記表現在是屬性的唯一入口 —— 不在表上的欄位系統不會問、也不會收。 所以規則要的欄位永遠拿不到，那一項會永遠停在資訊不足， 而且過程中不會有任何錯誤訊息。 三個可能的方向寫在 back_database_doc/README.md 的落差九。

T9 的範圍因此調整過：不是重寫一個規則引擎，而是寫一層轉接， 把 EligibilityResult 轉成 CandidateItem。 但「決定性條件」需要 Rule Engine 端配合輸出，不是 workflow 層能單方面補出來的 —— 而那是整個專案最強的差異點。

前後端之間的約定與待確認事項同樣有一份獨立紀錄： docs/front_back_doc/README.md。

怎麼跑起來、怎麼測

啟動後端

在 backend/ 目錄下：

  1. uv sync — 建立虛擬環境並安裝套件
  2. uv run uvicorn app.main:app --reload — 啟動在 http://localhost:8000

可用的端點：

方法路徑說明
GET/health存活檢查
POST/sessions建立諮詢，回應含 sessionId
POST/sessions/advance推進一步，需 header X-Session-Id
GET/sessions/current查目前狀態，需 header
DELETE/sessions/current立刻清除，需 header
這些端點回的是佔位資料：事件代號一律 spouse_death、 四個項目一律 pending、沒有任何資格判定。每個回應都帶 implementation 說明哪些能力還沒實作，前端可據此在畫面上標示。

跑 workflow 層的檢查

在 backend/ 目錄下：

  • uv run pytest tests/unit/test_workflow_state.py
  • uv run ruff check app/orchestration
  • uv run ruff format --check app/orchestration
注意：uv run pytest 跑完整套件目前會失敗。 資料層的四個測試檔用的 import 路徑是從 repository 根目錄算的， 而 backend/pyproject.toml 的設定是以 backend/ 為根，兩者對不上。 要跑完整套件得從根目錄執行 backend/.venv/Scripts/python.exe -m pytest backend/tests， 但那樣在 Windows 上還有 7 個測試會失敗（SQLite 連線沒有關閉，暫存目錄刪不掉）。 這個問題還沒有人處理。

還沒決定的事

  • 資格欄位登記表的實際欄位、選項與級距切點 — 由政策資料負責人依實際法規決定
  • 問題主題怎麼切（過世者／申請人／家庭…）— 待實際欄位確定
  • 互斥福利如何表達 — 領了 A 就不能領 B。benefit_programs.mutual_exclusion_text 已預留，但組合取決於尚未審核的官方文件
  • 辦理清單是儲存下來還是需要時即時推導
  • Session 存放的技術方案（記憶體、DynamoDB 或其他）與確切保存期限
  • 檢索與模型的暫時性失敗如何標記
  • Bedrock 模型、RAG 方案、AgentCore 與部署方式
